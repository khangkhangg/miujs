# Tour Studio — application benchmark

Generated by `bun bench/app.ts` (2026-10-15). Scenario: [bench/scenarios/tour-studio.ts](scenarios/tour-studio.ts).

- **Machine:** 4 × Intel(R) Xeon(R) Processor @ 2.80GHz, 16 GiB RAM, Linux 6.18.44-fc-v114. Load generator (2 Bun worker processes) and server share the machine.
- **Run:** 10 s measured after 2 s warmup, 64 concurrent connections, keep-alive.
- **App:** `apps/tour-studio` in production mode (`MIU_ENV=production`): SQLite (WAL) for data, sessions and
  rate limits, `diskBlobStore` for panoramas, JSON access log to a file, secure headers, sessions + auth on every
  request. Bun: `Bun.serve(app.serveOptions())`; Node: `serve()` from `miujs/node` with `--experimental-strip-types`.
- **Data:** the seeded demo tour (3 scenes, 2048×1024 PNG panoramas of 75 KiB, 75 KiB, 77 KiB) plus a
  creator's 2-scene tour created in `setup()` over HTTP.

## Analysis (hand-written, 2026-10-15; numbers above are from the run that produced this file)

**Headline.** The realistic mix runs at **~2.2k req/s on Bun and ~1.2k req/s on Node** with zero errors, p99 67 ms
(Bun) / 180 ms (Node) at 64 concurrent connections, and the server pegged at 100% of one core. That is ~20x below the
framework's own network numbers in [results.md](results.md) (41k req/s for `GET /user/:id`, i.e. ≲25 µs of
framework + server overhead per request). The profile agrees: `src/core` is 3.6% of self time. **The router,
context and middleware are not the bottleneck; the batteries the app is built from are.** Average server CPU is
~450 µs per request, spent in:

1. **SQLite reads through `Repository.list()` — the #1 cost (~30% of CPU).** Every list is two statements (rows +
   `COUNT(*)`), and the rows query costs 20–45 µs in the running app even for 1–5 rows (JSON documents,
   `ORDER BY json_extract(...)` → temp B-tree; measured with an instrumented driver: 46 µs scenes, 41 µs tours-by-slug,
   34 µs hotspots per public bundle). The public tour bundle — 35% of traffic — does three lists (slug lookup,
   scenes, hotspots) plus three unused counts on *every* request and has no cache: ~360 µs per bundle in-process.
   Fixes, biggest first: cache the bundle per tour keyed by a version the DB owns (e.g. bump `tour.updatedAt`
   on scene/hotspot writes, then one `tours.get` decides), let `list()` skip `COUNT(*)` (`{ count: false }`), and
   use `get`-by-unique-index for the slug lookup.
2. **SQLite writes fsync on every commit (~18% of CPU for 10% of traffic).** `openDatabase()` enables WAL but
   keeps `synchronous=FULL`, and the driver is synchronous, so each fsync blocks the event loop: ~336 µs vs
   ~83 µs per write in isolation. Switching to `NORMAL` (variant table) gives **+20% total throughput** and cuts
   the write step's p50 from 46 to 38 ms. Recommend `NORMAL` as the WAL default (see framework-bugs test).
3. **Disk blob store round-trips (~6%, and most of the media latency).** Each `get()` does `realpath` + read the
   JSON sidecar + `open`; 304s pay all of it and then cancel the stream (`serveBlob` never uses `head()` for
   conditional requests). On Bun the response also loses `Content-Length` (chunked), which disables sendfile-like
   fast paths. Media p50 is ~34 ms on Bun but **~110 ms on Node**, where every awaited fs hop waits a full
   event-loop turn behind other requests (it is not libuv thread-pool starvation: `UV_THREADPOOL_SIZE=16` changed
   nothing). Fixes: cache sidecar metadata, `head()` for conditional requests, return a Blob/BunFile slice.
4. **Per-request crypto via WebCrypto (~5%).** The bundle ETag is a SHA-256 over the JSON body
   (`crypto.subtle.digest`, ~80 µs on Bun including the async hop), session cookies are HMAC-verified and API keys
   SHA-256-hashed per request. A cached bundle (1.) removes the digest; a cheap sync hash would do for an ETag.
5. **Access log (~4–10%).** One `console.log(JSON.stringify(...))` per request to a file: +5–10% throughput when
   off (variant). Fine for production, but a buffered/async sink would be cheaper.
6. **MCP `tools/list`** re-serialises ~40 tool schemas per call (`Response.json`, ~1% of CPU at 5% of traffic);
   the list could be serialised once.

**Node vs Bun.** Node reaches 55% of Bun's throughput with 1.75x the memory (142 vs 81 MB peak RSS). Non-media
steps are close (bundle p50 26 vs 23 ms) because both are CPU-bound on the same SQLite work; the gap is the media
path (above) and the Web-streams-over-`node:http` bridge in `writeResponse`.

**Correctness under load.** 22k (Bun) and 12k (Node) requests including ~2.2k/1.2k write pairs: zero errors, no
SQLite busy errors (one connection per process), no leaked file handles (client aborts are cancelled correctly;
only *unread* bodies leak — see framework-bugs). `test/e2e/tour-studio/load.test.ts` keeps this in CI.

**Caveats.** One run per configuration; load generator and server share 4 cores, so treat differences under
~10% as noise. The synthetic panoramas compress to ~75 KiB; real 8K JPEG panoramas are 5–15 MB, which would make
media throughput I/O- rather than CPU-bound and makes the missing Content-Length/sendfile path matter more.
